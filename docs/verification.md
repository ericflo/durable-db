# Verification

This page records what is claimed, what has been checked, how, and what has not. Bounded model checking is evidence about a model, not a proof of the Rust implementation or of every deployment.

## What is claimed

For one database, under the storage assumptions below:

1. **Durability and one history.** Every acknowledged transaction, together with the exact sequence of transactions before it, can be reconstructed from the bucket alone. All acknowledged histories are therefore prefixes of a single sequence: nothing acknowledged is lost, reordered or forked, whatever servers crash, pause, race or are replaced.
2. **Linearizable reads.** A `strong` read reflects every transaction acknowledged before the read began.
3. **Safe collection.** No server deletes an object that the current owner, or any later owner, needs.
4. **Final deletion.** Once any server has concluded that a database is deleted, no server acknowledges anything for it again. A deletion that did not complete leaves the database either intact or deleted, never in between.

## Assumptions

- **Storage** provides read-after-write consistency for PUT, DELETE, GET, HEAD and LIST, and never exposes a partial object. It may be arbitrarily slow, fail any request, and lose any response. A listing reports each key as it was at some moment during the listing, in key order.
- **Servers** stop without warning, pause for any length of time and resume, and run with arbitrary relative speeds. They do not run corrupted code or forge each other's objects: all servers of a deployment are trusted with the bucket.
- **Uploads** a server has sent may arrive late, more than once, and after the server has crashed.
- **Clocks** are not assumed to agree, or to be correct at all. Token expiry is the only place a clock is read, and it affects authorization only.
- **Membership** may be wrong or disagree between servers.

## The model

[`spec/DurableDb.tla`](../spec/DurableDb.tla) specifies creating a database, taking ownership, committing, linearizable reads, checkpointing, collection and deletion for one database, as atomic steps on a store of claims, manifests, frames and the tombstone. The store starts empty. Writers crash at any step. Any upload ever sent may arrive at any later time, any number of times, including after its object was collected.

Four invariants are checked in every reachable state:

| Invariant | Meaning |
| --- | --- |
| `Durable` | Every acknowledged history is a prefix of what a reader reconstructs from the store, unless the database was deleted. |
| `FreshReads` | No checked read missed a transaction acknowledged before it began. |
| `OwnerIntact` | The newest checked manifest of a writer whose claim still stands has not been deleted. |
| `Final` | Once a writer has concluded that the database is deleted, no writer is serving with a claim that stands. |

```sh
scripts/check-model.sh        # about three minutes; capped at 2 GiB heap, four workers and ten minutes a configuration
```

**Results** (TLC 2.19, 2026-11-14), each an exhaustive search with no violation:

| Configuration | Bounds | States generated | Distinct states | Depth |
| --- | --- | --- | --- | --- |
| `DurableDb` | 2 writers, epoch numbers up to 2, 2 transactions, no deletion | 27,663,022 | 3,585,296 | 61 |
| `Deletion` | 2 writers, epoch numbers up to 2, 1 transaction, deletion at any time | 23,717,105 | 4,110,075 | 67 |
| `DeepDeletion` | 2 writers, epoch numbers up to 2, 2 transactions, deletion at any time | 479,947,461 | 67,082,438 | 74 |

The first two configurations exist because deletion with two transactions is a much larger state space. `spec/DeepDeletion.cfg` is that combination. It is not part of the default run, because it takes nineteen minutes where the others take three together:

```sh
TLC_TIMEOUT=3600 scripts/check-model.sh DeepDeletion
```

For a search of this size TLC reports how likely it is that two distinct states had the same fingerprint and one was therefore not looked at: 0.0015 by its calculation, 0.00019 by the fingerprints it saw. An earlier version of this page said that a run of this configuration had been stopped after 24 minutes and 92 million distinct states. With the model and the configuration as they are in the repository it ends with fewer states than that, so that run was not of this model; which it was of is not recorded.

The epoch number a writer chooses is unconstrained in the model (any unused number), so safety does not depend on the hint the implementation uses.

### Negative controls

Each protocol rule is a switch in the model. Turning one off must produce a counterexample; if it did not, the model would not be testing that rule. All eleven are refuted:

| Rule turned off | Configuration | Violated |
| --- | --- | --- |
| Acknowledge only after a claim check that began after the frame was stored | `UnsafeAckWithoutCheck` | `Durable` |
| Withdraw when a higher claim is listed | `UnsafeIgnoreHigherClaim` | `OwnerIntact` |
| Withdraw when a higher epoch already has a manifest | `UnsafeIgnoreHigherManifest` | `Durable` |
| Delete lower claims before reading manifests and frames | `UnsafeReadBeforeRevoke` | `Durable` |
| Collect only after a claim check that began after the manifest was stored | `UnsafeCollectWithoutCheck` | `Durable` |
| Never use a claim whose upload may still be in flight | `UnsafeRetriedClaim` | `OwnerIntact` |
| Never delete the own claim while an own manifest upload may still arrive | `UnsafeReleaseWhileSending` | `Durable` |
| After revoking, give the claim back only when a higher epoch outranks this one | `UnsafeGiveBackAfterRevoke` | `Durable` |
| Expose recovered state only after a claim check that follows the first manifest | `UnsafeServeBeforeCheck` | `Durable` |
| Write the tombstone only after a claim check that began after a manifest marked deleted was stored | `UnsafeTombstoneWithoutCheck` | `Final` |
| Remove a deleted database's objects only once the tombstone is stored | `UnsafePurgeBeforeTombstone` | `Final` |

### What the model leaves out

- **Tables** are folded into the manifest's state. Their collection follows the same rule as superseded manifests, which is modelled, with one exception that is not: the table a merge was uploading when its database was released, deleted or closed is deleted by that upload once it ends, whatever claim its server holds then (since 2.1.10). No manifest lists such a table or can come to: only one of its own epoch could, and its merge has ended. So no state the model holds refers to it, and deleting it removes nothing a reader could be sent to.
- **Transactions are unconditional.** Version checks, range checks and idempotency keys are not modelled. A refusal is treated by the implementation as a read: it is reported only after a claim check of its own.
- **Deletes are atomic steps.** A delete request that takes effect long after its sender gave up is not modelled. The argument that it is harmless is informal: a delete is sent only for an object the sender was entitled to remove for good, and the only object whose reappearance would matter, a claim, is uploaded once. The chaos test does inject such deletes.
- **Only safety** is checked. That some server eventually makes progress is not.
- **The bounds are small.** Two writers, two epochs and one or two transactions cover every interleaving of one takeover with commits, a flush, collection, a deletion and late uploads, not longer chains.
- **Nothing connects the model to the Rust code** except that the code is written to follow it step for step and the tests below.

### What these checks found

The chaos test found three defects in the first implementation of this protocol, each within seconds. They are listed because they show what the checks are able to catch.

1. After a failed takeover the server deleted its claim although its manifest upload could still arrive. A lower epoch could then serve, and the late manifest would hide its acknowledged writes. The model forbade this step; the implementation had not followed it. It is now the `UnsafeReleaseWhileSending` control.
2. State recovered at takeover, including transactions the previous owner stored but never acknowledged, was visible before a claim check confirmed it. Now the `UnsafeServeBeforeCheck` control.
3. A stale owner could answer "conflict" from old state, so a client concluded that a transaction it had in fact committed was not applied. Refusals now wait for a claim check.

Release 2.0.0 was then reviewed in three parts (the engine, the storage layer, and the HTTP and tenant boundary) by automated reviewers instructed to break it and to prove each finding with a failing test. What they confirmed in the engine and the storage layer, all fixed since, each with a test that fails on the old code:

4. **Deletion was outside the protocol.** The owner checked its claim and then wrote the tombstone. A server that took over between the two served the database and acknowledged writes, and the tombstone then arrived and deleted it. Deletion is now a manifest settled by a claim check that follows it, modelled, with the `UnsafeTombstoneWithoutCheck` and `UnsafePurgeBeforeTombstone` controls.
5. **A takeover that failed after revoking gave its claim back.** The revoked epoch's first manifest could still arrive. A third server could then choose a number below it, serve, and have its acknowledged writes hidden when that manifest landed. Now the `UnsafeGiveBackAfterRevoke` control.
6. **A purge could make a revoked claim readable again** on a bucket that keeps versions, when a listing page ended between the claim's delete marker and the version under it. On Backblaze B2 the old code showed the key during the purge; `tests/bucket.rs` reproduces that arrangement.
7. **A listing page that held nothing but said there was more** ended the listing, so a claim could be missed at takeover. Whether a provider sends such a page was not established; the client no longer depends on it.
8. **Two directory stores on one directory could exchange temporary files** when they shared a process id, as two containers on one volume do, and acknowledge an object holding another's bytes.
9. A lookup that overlapped the owner's own merge reported the database lost and closed it. An inverted range stopped the writer. A refusal could report a conflict with a write that was never committed. A crafted table footer panicked instead of reporting damage. Keys that are not UTF-8, accepted only by the library interface, became unreadable once flushed; they are now refused.

The same review of the HTTP and tenant boundary confirmed the following, also fixed, each with a test in `tests/tenants.rs`, `tests/engine.rs` or `tests/interleavings.rs`. Undoing any one of the fixes makes its test fail; that was checked for each.

10. **Memory was committed to callers who had not shown a token.** A request's body was budgeted and read before its token was checked, a request with no body was charged for the largest one, and nothing limited how long a body, a request head or an unread response could take. A few hundred connections that sent nothing could hold the whole budget and refuse every other caller. The token is now checked against the database in the path first; bodies and results are reserved for exactly, with a quarter of each budget per database; and every phase of a connection has a time limit.
11. **A read was limited after it had been put together.** One request could name thousands of scans over deleted keys still in memory, or thousands of large values, and have all of it gathered before being told it was too much. A request's arrays were likewise parsed in full before being counted. Both are now counted as they grow.
12. **A response nobody read stayed in memory** for as long as the connection did. It is now part of the result budget until it is written, and the connection is closed when the client takes nothing for 30 seconds.
13. **A stored value kept its whole request alive.** A small value sent in a large body pinned that body in memory until the next flush, uncounted. Values are now copied out of the request.
14. **Deletions were exempt from back-pressure**, so a database could fill memory with them while a flush was behind.
15. **Two configuration changes made at once could lose one**, for instance a token revocation. Changes are now applied in the writer, to the configuration as it stands.
16. **A relayed path could be read differently by the next server**, because the HTTP client normalizes `.` and `..` segments and backslashes. Access was still checked there, so no data crossed tenants; such paths are now refused by every server. **Any caller could mark a request as relayed**, which made a server take over a database the caller had a token for. The mark is now a proof made with the signing key.
17. Logs named databases. They now carry a tag derived from the name. A token lifetime near the largest number wrapped around. `/readyz`, which anyone may call, asked storage on every call.

The engine was then read for whatever it holds in memory that no flag limited, so that the memory a server needs could be stated. Found and fixed, each with a test that fails when the fix is undone:

18. **A merge built its whole result in memory**, and so needed as much memory as the database it merged. A merge now writes tables of 32 MiB, one at a time.
19. **Every table kept its index for as long as its database was open.** An index can be as large as its table. Indexes are now held by the cache, within `--cache-bytes`.
20. **The keys remembered for range checks were limited in number only**: 100,000 keys of the largest size are 112 MiB, for each open database that wrote that many. They are now limited in bytes, for a database and for the server.
21. **An empty disk cache fetched every table that was read, whole, all at once**: after a restart, as many tables in memory as were being read. Two are fetched at a time.
22. **A database waiting for its turn to merge stopped flushing**, so two long merges of other databases could make it refuse writes. **A merge held up its own database's flushes and its release** until it was done. A waiting database now goes on flushing, and a merge gives way between two of the tables it writes.

A server from before these changes ignores what a manifest says about runs and reads each table on its own, which gives the same answers.

23. The first version of the fix for 22 asked for a new turn as soon as a merge failed, and was given it at once: **a merge that could not reach storage was repeated without pause.** The 200 chaos seeds passed all the same. One run made while the machine was busy with other work did not end, and that was the only sign. It was reproduced by holding the test to a fraction of a CPU, found in a core dump, and fixed: a failed merge now waits for the database's next write. Two things follow. A chaos seed does not fix the whole schedule, because the engine reads the wall clock for its storage deadline and its idle flush while the test's storage runs on a simulated clock; a schedule can therefore depend on how fast the machine is. And a schedule that did not end used to look like a slow run; it is now stopped and named.

38. **A server went on sending a store what it refused.** The 28,000 uploads of finding 37 were sent by design. An upload that fails is sent again at once, up to four times on Backblaze, and all of that again after 10 ms, after 20 ms and so on up to a second, for the thirty seconds a database gives its storage. A read or a deletion that fails is sent seven times. Nothing in this looked at whether the store was taking anything at all.

    Since 2.1.5 a server counts refusals, for each kind of request apart: reads, changes, and on Backblaze B2 the uploads to its storage pods and the calls that name a pod. A refusal is an answer for which a request is sent again: `429`, `408`, a `5xx` other than `501`, a connection that failed, a request that stalled. After eight in a row, with no request of that kind taken between them, requests of that kind fail in the server without being sent. After one second, or after as long as the store asked for in `Retry-After` up to a minute, one request is sent, and the others go on failing until it is answered. If it is taken, all are sent again. If it is refused, the wait doubles, to four seconds at most. The kinds are counted apart because a store limits them apart, and a read that is taken would otherwise hide uploads that are all refused. The waits are short because what spares the store is one request in place of hundreds, and a longer wait is that much longer without the store once it takes requests again.

    A request that fails without being sent has stored nothing, and every caller already had to allow for a request that failed and stored nothing: the protocol and the model are unchanged. The server logs the eighth refusal, and each request it tries after that and has refused, with the store's status, its error code and the wait it asked for; and it logs when the store takes requests again.

    It is tested in three ways. The counting runs against a clock the tests set: seven refusals and then a request that is taken, a hundred times over, hold nothing back; one request at a time is tried; a request on trial that is given up lets another be tried; requests that were under way when the store began to refuse change nothing by being refused late; a store is left alone for as long as it asks. Two stand-ins are refused to: the S3 stand-in as in the table above, and a stand-in for Backblaze's API that refuses every upload, of which eight are sent, and then of sixty more none is sent, none takes an upload URL from those the server holds, and none calls for a new one. 27 faults put into it one at a time each fail a test. And `scripts/test-refusals.sh` puts a proxy that refuses in front of a real S3 server, with the figures in the table above.

    On Backblaze B2 itself, at a rate under the limit of its documentation, nothing was held back: in two minutes of 87 commits a second over 8 databases, about 255 requests a second, 9 of 21,257 uploads were refused, each was followed by one that was taken, and the server logged no warning. The Kubernetes run of the table above passed with 2.1.5 as well.

    Two things it is not. It is not a rate: a store that takes some of what it is sent is sent all of it, so an account a little over its limit is sent as much as before. And it has not been seen on Backblaze. The refusal of finding 37 was not made again, for the reason given there, so what Backblaze says when it refuses has still not been read. The next time it happens it is in the server's log.

40. **A slow store held up a deletion, a release and a server's housekeeping.** In the run of finding 39 with that change, on a MinIO that took more than twenty seconds over a listing, the 256 deletions took twelve minutes, one of them seven, and one round of the server's housekeeping ran for over two minutes, which the log said every thirty seconds.

41. **A database that reached its quota stayed there.** A database's size counts every table it has stored, and a value that was written over or deleted is stored until a merge reaches the table that holds it.     Now a write that the quota has no room for asks for everything to be merged, when the database has more than one run of tables or has writes that are in no table yet, and is answered `503` while that is done, as a write is that waits for a flush. It is taken when the merge has made room, and answered `507` when it has not, or when there was nothing to merge. With the change the first run made 493 writes a second for the forty seconds and none failed; the clients were told to wait 83,833 times, by a benchmark that asks again at once. In the second the write of 2 MiB was told to wait, since what had been deleted was not merged away yet, and was taken 2.6 s later; the database then held 2 MiB. Those seconds are the wait after the merge that the fill had ended with, which had made no room.

    A merge of everything rewrites the database, and a database that is full of what can still be read would ask for one with every write. So after such a merge that removed less than an eighth of what it merged, the next waits four times as long as that one took, and a second at least; a write with no room is answered `507` meanwhile, or `503` if something has been deleted since that merge, which the next will take in. As first written, a deletion ended the wait, since it is how room is made. Then a client at a full quota that deleted one key and wrote one had everything merged for that write, and for the next: two requests for a rewrite of the database, as often as it could be rewritten. Only time ends the wait now. A merge for the quota also flushes first: one that began with a write still in no table left the value it had written over in place, and was then waited after.

    The protocol is unchanged: this is the merge a database then made when it had more than twelve runs, which since 2.1.8 merges only the newest of them (finding 44). Four tests in `tests/engine.rs` and two in `tests/interleavings.rs`; 15 faults put into it one at a time each fail one. Found by filling a database and writing over it, when the question was what a larger quota would cost.

42. **A merge that took longer than a database may be idle would never have been finished.** A server releases a database that has not been used for five minutes (`--idle-seconds`), and a merge under way stops at a release. Use meant requests. So a database whose clients went quiet while it was merging was released in the middle, what the merge had uploaded was discarded, and the next owner began the merge again from its start when the database was next written to. A merge of everything a database holds takes as long as reading it and writing it again: at 50 MiB a second, five minutes is 15 GiB. Below that it was a merge made twice now and then. Above it, a database written in bursts would never finish one, and its tables would grow in number, with what is counted against its quota. This was read in the code while larger databases were measured; no run has shown it, since none has had a merge that long. A merge is now use, when it begins and with each table it stores. One test in `tests/interleavings.rs` holds back each table of a merge, runs the server's housekeeping meanwhile, and expects the database to stay; 2 faults fail it.
43. **A server that read more than its disk cache held fetched tables over and over**, in every release up to 2.1.7, which reported it and did not fix it. The disk cache kept whole tables and, over its budget, put out those that were written longest ago. A read whose table was not there read the block it needed from the store and had the whole table fetched behind it, two tables at a time. That table took the place of others, which the next reads missed in their turn. When the databases a server read were larger than its cache, this did not end. `scripts/soak-size.sh` with a database of 4 GiB and the manifest's cache of 1 GiB, on a local directory: 14,228 reads a second of values of 4 KiB, which is 56 MiB a second to the clients, and 73,388 MiB read from the store in that minute, which is 1.2 GiB a second and twenty-two times as much. By the server's count of its requests, three for every two reads, some 0.7 GiB a second of that were the blocks the reads asked for, 32 KiB for a value of 4 KiB, which is the cost of a read that finds its table in neither cache. The rest were whole tables, some sixteen a second, and those did not depend on how many reads there were: one read that missed was enough to fetch a table. A local directory gave that at once. A bucket gives it at the speed of the link and bills it as download, and meanwhile most reads wait for the bucket. A merge of tables that were not in the cache read them a block at a time, a thousand requests for a table of 32 MiB, and had each fetched as well: while that database was filled, 9,846 MiB were read back of the 28,230 MiB that were sent. Nothing wrong was answered, and memory was not affected. It was found by the count of bytes read from storage that the script of 2.1.7 prints beside each of its loads; no earlier measurement had a database larger than the cache.

    Since 2.1.8 the cache knows what it holds, and in what order that was used, without asking its directory. A table this server wrote is taken as before, and the least recently used make way for it. A table that reads miss is read from the store a block at a time until they have had a sixteenth of it, so that what is fetched is never more than sixteen times what was read, where one read of 4 KiB had fetched 32 MiB. It is then fetched into room that is free, or that tables no read has asked for in five minutes leave, and never in the place of a table in use. A merge reads each of its tables once and has none fetched, and what it replaced leaves the cache when it leaves the manifest. A scan, which a merge is, asks the store for one block, then two, then four, up to 64 blocks or 1 MiB in a request, and for nothing past its own end.

    Two things were wrong in that change as it was first written. Both were found by reading it again before it was measured, and no test had shown either. To see whether a table had room, every read that missed walked the tables that had gone unread, with the cache's lock held: a server with thousands of small tables unread, and not enough room among them for a large one, would have walked them all for each such read. A read that misses now looks at one table, and tables that have gone unread are put out as they are found. And what a scan had read ahead was in memory, 2 MiB for each run of tables it read, with nothing to bound how many scans did so at once: some hundreds of scans of large databases would have passed a server's memory limit. Now sixteen scans of requests and sixteen runs of tables in merges read ahead at a time, 1 MiB each, the others read a block at a time, and a request's scan reads ahead only in a table that is not on the disk. The cache also holds no more than 262,144 tables, so that what it remembers of them is 40 MiB at most.

    Four more were found by a second reading, by a reader that had not written the change, before it was released. None of them answered anything wrong. A damaged copy in the disk cache is discarded by the reader that meets the damage, which then reads the store's. A second reader that had the copy's bytes at the same time found nothing left to discard, and was answered that the table is damaged though the store's was whole. That was so for two reads of a block in every release; a scan that reads ahead holds up to a megabyte of the copy, and for longer. A reader on a server with a disk cache now reads the store's once before it says so, whoever discarded the copy. A scan kept what it had read ahead, and its turn, after it had come to the last block of it. A merge keeps the scans of the runs it has read through until it has published, so a merge of thirteen runs left three turns to the other. A scan now gives both up when the block it comes to next is not among those it read. The cache removed the files of the tables it put out with its lock held, and every read of a table waits for that lock: a table of 32 MiB written into a cache of small tables could remove thousands. They are now removed when the lock has been let go. And a table that was written, and that would not fit beside the room promised to tables being fetched, put out every table before it found that out. It now puts out none; that needed a cache of under 200 MiB.

    Three more were found by measuring it, before it was released. None of them answered anything wrong; each had a server read from its store what it had held on its disk. A table that a merge stores is put into the cache, and the least recently used made way for it. In a merge those are the tables it has not come to yet: every table it has read was used after them. A merge of everything, in a cache as large as the database, so put out its own tables ahead of itself and read them from the store, and since a merge reads and stores one table after another, each such read took its turn with an upload. On Backblaze B2 a write at the quota of a database of 1 GiB waited 752, 906 and 1,020 seconds in three runs of `scripts/soak-size.sh`, where 2.1.7 had waited 525; on a local directory, 838 MiB were read back while that merge stored 1,053 MiB. A table a merge stores now never takes the room of a table that merge has yet to read through, and is not kept when there is no other room: that the merge will read those tables is certain, and that its own table will be read is not. With only that rule the same run still read back 549 MiB, where the database held 210 MiB more than the cache: a merge whose tables were all in the cache left half of its result there. The tables it stored had made way for one another, and for what else was in use, while the tables it had read through stayed until it was published and then left. A table a merge stores now takes room that is free, then that of a table no read has asked for in five minutes, then that of the tables its merge has read through, and only then that of the least recently used. And a table that a read had missed was fetched in the background while a merge replaced it; it arrived after the merge was published and was kept, though no manifest listed it, and counted as in use for five minutes, like one that had just been read. After a merge of everything under 64 clients' reads, in a cache of the database's size, one such table kept the last table of the result out, and one read in thirty went to the store. The cache now remembers which tables have left their manifests, up to 65,536 of them, and neither fetches nor keeps one. With the three, the merge for the quota in that run read back 354 MiB, where the database held 316 MiB more than the cache, and after a merge of everything under reads the store was asked for nothing. What it costs: while a merge runs in a cache that has neither free room nor a table that has gone unread, requests read the tables that merge has read through from the store, until it is published.

    Three more were found in those rules by a third reading, again by a reader that had not written them, before they were released. None of them answered anything wrong. The tables a merge has stored are read by nothing until it is published, and a merge of a few gigabytes into a slow store runs for longer than the five minutes after which a table counts as unread. Its first tables then made way before any other, for its later ones and for tables fetched for requests. The flush that a merge gives way to between two of its tables stored its table by the order of use alone, and could put out a table the merge was coming to. A table that is stored while a merge runs, by the merge or by a flush it gives way to, now never takes the room of a table that merge has yet to read or has stored, however long the merge runs. And what the cache remembers of the tables that left their manifests was forgotten all at once when there were 65,536 of them, with those that had only just left, and one manifest that dropped more than that was remembered whole. The first to leave is now the first forgotten, and there are never more.

    A fourth reading, of those three changes, found nothing that answers wrong, loses a table or breaks the cache's counts, and three things the rules do not cover, which stay as they are in this release. Against a table fetched for a request and against a table another database stores, a merge's tables are in use as any table is: used when the merge last stored a table, and unread five minutes after. A merge that stores nothing for that long, as when a flush it gave way to waits for the store, can so have them put out, and reads from the store those it had yet to read. The cache removes a file after it has let go of its lock; a table that is put back in between, by a fetch that arrives just then, is counted as held with no file, until the next read of it finds that out and reads the store's. And a read that is answered from the cache in memory is not use of the table on disk: a table whose blocks in use are all in memory counts as unread on disk after five minutes.

    The protocol and the storage format are unchanged. Ten tests of the cache by itself in `src/io.rs` and thirteen in `tests/interleavings.rs`, and the test of a damaged cache in `tests/engine.rs` now expects the cache to hold the manifest's tables and no others; 92 faults put into the change one at a time each fail a test. What remains, beside what the fourth reading left, is what a read beyond both caches costs: a request to the store for each run of tables it looks in. And in use means read from the disk in the last five minutes, not read the most.

46. **A database that waited for a turn to merge gained a run with every flush, and a release waited for the upload of a merge's table.** Both were stated as limits of 2.1.9 (finding 45). A server merges two databases at a time, and a merge held its turn from its first table to its last: for a database of 4 GiB, half a minute on a local directory and far longer over a bucket.     - A merge gives its turn to a database that waits for one between two of its tables, and waits for a turn again. A merge that waits for its turn flushes what falls due, is use, and holds where it is in each run and no more: not what it had read ahead, nor any index. Its database takes writes as one that waits to begin a merge does, and counts the merge's runs again once it has its turn. A merge behind a merge has no turn of its own to give.

    - A release or a deletion does not wait for the upload of a merge's table. The upload goes on alone, one attempt at a time, and deletes what it stored once it ends. No merge is begun once a release has, including after the flush that a merge for the quota makes first.

    - The first found that a merge that waited for its turn again still counted as merging, so that its database refused writes that nothing would merge meanwhile; that a merge's small tables were raced as a flush's are, so that a release waited up to ten seconds for their attempts, and one could land after the upload had deleted what it stored and stay in a database that had been deleted; that an upload was begun after a release had; that a merge that waited held an index and a block of each of its runs, and that any number of merges might wait; and that two tests passed without the code they were written for.
    - The second found that nothing pinned that a merge counts its runs again once it has its turn; and that a merge could begin after a release had, after the flush that the maintenance makes, read all it needed from the disk cache, where a release stops nothing, and upload its table. And that a request the store applies after it reported it failed may land after the upload's delete, as it may for any upload.
    - The third found the same of the flush that a merge for the quota makes first.

    Two checks that the first form added were taken out: one that a merge begins no upload once a release has, and one that a merge that has its turn again as a release begins goes no further. With them, two faults of finding 44, which take out the checks that stop a merge after a release, no longer failed a test, since such a merge then stored nothing either way, and no test could tell either check from its absence.

    `scripts/soak-tenants.sh` with 2.1.9 and then 2.1.10, one run of each, the afternoon 2.1.10 was released, on a local directory ([performance](performance.md#several-databases-merging-at-once)). While two merges of 4 GiB held the server's turns, a small database written by 64 clients went from 2 runs to 27 with 2.1.9 and was read at 45,580 keys a second at the least; with 2.1.10 it had 5 runs at most and was read at 114,316 at the least. The two merges took a tenth longer, 52.5 seconds where they had taken 47.5 and 48.3. Three merges of 2 GiB, which 2.1.9 ended after 24.5, 25.3 and 42.7 seconds, 2.1.10 ended after 37.7 to 38.6.

    The protocol and the storage format are unchanged. One object is deleted outside the rule the model checks: the table of a merge whose upload a release, a deletion or a takeover stopped waiting for, by that upload, whatever claim its server holds by then. No manifest lists it or can come to ([model](#what-the-model-leaves-out)). Twelve tests in `tests/interleavings.rs` are new, one of them the disk-cache test of what a merge is coming to with the flush made while the merge waits for its turn, and two were changed; a test in `tests/engine.rs` waits for merges to end before it counts the indexes in memory, since a merge holds those it reads. 25 faults put into the change one at a time each fail a test, and the 29 of finding 45, the 49 of finding 44 and the 92 of finding 43 still do.

    What remains. While more databases have a merge to make than a server has turns, their merges take turns a table at a time, and each takes longer than with a turn to itself: the first two of three merges of 2 GiB ended thirteen seconds later. A merge that gives its turn up reads again what it had read ahead and the indexes of its tables, which on a bucket is download; that has been measured on a local directory and not on a bucket. A merge that reads all it needs from the disk cache when a release begins goes on to the end of its table, uploads it in the background and deletes it. A request that the store applies after it reported it failed may land after that upload has deleted its table, and stay. Writes wait while a merge would leave a database with more than 24 runs, a figure chosen and not measured against others, and a merge that fails every time is begun again for every write that is taken.

## Remaining obligations

- Send the request that removes many versions to Amazon S3, to Google Cloud Storage and to a store that refuses it. It has been sent to Backblaze B2, a community build of MinIO, RustFS and Garage, which all take it, and to a stand-in that refuses it.
- Run the bucket tests and benchmarks on Amazon S3, Cloudflare R2 and Google Cloud Storage. The code path is shared with B2 except for the upload call, and has been run on three S3 servers that were each one process on one machine, which says nothing of a provider's consistency across its own machines. What Amazon and Google answer without an account is in finding 35. R2 answers nothing without one: its documentation lists the request that lists versions as not implemented, and what it answers to that request, which decides whether a server starts there, has been read about and not seen. On Google Cloud Storage a bucket's soft delete, which Google's documentation gives as on for a new bucket, keeps what is removed for seven days more; whether a purge is then complete has not been tried.
- A soak of many hours under load with periodic failures, on a real multi-node cluster rather than kind. What has been run is half an hour on one desktop with a server stopped every ten seconds (`scripts/soak-kills.sh`).
- The memory soak for hours, and on a provider's bucket, where an upload stays in memory for as long as the bucket takes to store it. On a local directory it has run for ten minutes a load, and on MinIO on the same desktop for twenty minutes of 256 databases (`scripts/soak-bucket.sh`, finding 39): memory was level in both. On Backblaze B2 with the default flags it was still rising after eleven minutes (finding 37).
- A store that is slow holds up more than the request that waits for it. A collection holds its database's next flush for as long as one purge takes to fail, which is a minute when a listing is not answered; and the sweep of what an earlier owner left, one listing of the whole database, does not give way to a release as a collection does (finding 40).
- Which tables a disk cache smaller than what its server reads should hold. It keeps those that were read in the last five minutes, whichever came first, and does not count how often each is read; a server that writes much through such a cache fetches again what its writes put out. Neither has been measured under a load that changes.
- One database larger than 1 GiB on a provider's bucket, larger than 16 GiB anywhere, or larger than its server's disk cache on a bucket. What a write at the quota waits for, a merge of everything, has been timed over one desktop's uplink only.
- Model conditional transactions with idempotent retries, and a delete request that arrives late.
- Check a liveness property: with one correct server and working storage, a request is eventually answered.
- Make the chaos test repeatable from its seed alone, by giving the engine the simulated clock for its deadlines, and run it routinely under CPU pressure as well as without.
- The rule for choosing storage pods on Backblaze B2 was measured from one desktop on Wi-Fi, for minutes at a time. A server in a data centre, and hours of load, have not been measured.
- A server sends requests as fast as its databases commit and keeps itself under no rate. It holds back from a store that refuses everything of one kind (findings 38 and 39), which has been seen on stand-ins and behind a proxy and not on Backblaze B2, whose refusal (finding 37) was not made again. What Backblaze answers then, with which code and `Retry-After`, has not been read.
- A round of a server's housekeeping that does not end is reported every thirty seconds since 2.1.6, and nothing takes its place: it is not ended, since what it holds is not known. The one that was long waited for releases, which none does now (finding 40).
- Writes wait while a merge would leave more than 24 runs (finding 45). Over a slow link it was not reached, and a bound of 12 held writes back without holding the runs down ([performance](performance.md#over-a-slow-link)); how often a database on a provider's bucket reaches it has not been measured. Merges that take turns a table at a time (finding 46) have been measured on a local directory and not on a bucket, where what a merge reads again after giving its turn up is download.
- A review by people outside the project. The reviews recorded above were automated and commissioned by the project itself.
- Behaviour when the bucket itself misbehaves beyond the assumptions (lost objects, stale listings) is undefined; block checksums detect corrupted table data only, and a manifest carries no checksum of its own.
