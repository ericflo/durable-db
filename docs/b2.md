# B2 publication protocol

Status: design and implementation in progress. B2 is a required authoritative backend, including multi-pod deployments.

B2's [native bucket update](https://www.backblaze.com/apidocs/b2-update-bucket) accepts `ifRevisionIs`. The operation updates bucket metadata only when the stored revision matches. [Bucket listing](https://www.backblaze.com/apidocs/b2-list-buckets) returns both the revision and metadata. This supplies a candidate atomic publication point without relying on unsupported conditional file overwrites.

Data pages and manifests remain immutable B2 files. Small bucket metadata pointers select the current immutable state. Writers upload first, then conditionally publish the pointer. A timeout is an unknown outcome; receipts recover acknowledgments. Scaling API pods does not change the authority or require peer consensus.

The implementation must preserve unrelated bucket metadata, bound metadata size, handle stale revisions and lost responses, and collect exact file versions. It must model the extra immutable manifest layer and protect it from concurrent collection. Bucket metadata changes serialize within a bucket; adding pods does not eliminate that contention. Benchmarking and batching/partitioning design are required before performance claims.

The metadata API needs `listBuckets` and `writeBuckets`. B2 restricts which capabilities can be attached to bucket-restricted application keys. Deployment documentation must spell out the credential scope; use an isolated account or an appropriately isolated authority service where required. Credentials are never exposed to database tenants.

Cloud qualification remains outstanding: API rate limits, fresh read semantics, concurrent conditional updates, injected lost responses, cache-free recovery, version deletion, and 1→N→1 deployment tests. An adapter test against an emulator is not evidence that B2 itself provides every assumed guarantee.
