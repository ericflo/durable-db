# B2 publication protocol

Status: the shared B2/S3 publication implementation passed fault tests, bounded models, and an initial real-B2 integration test on 2026-11-08. Extended contention, scaling, and soak qualification continues.

## Authority without a separate coordinator

B2's [native bucket update](https://www.backblaze.com/apidocs/b2-update-bucket) accepts `ifRevisionIs`. Only the matching revision can update bucket metadata. [Bucket listing](https://www.backblaze.com/apidocs/b2-list-buckets) returns revision and metadata. This supplies the publication point without conditional file overwrites.

The S3-compatible API carries immutable data pages and immutable manifests. One `durable-db-heads` bucket-info value holds the bounded directory of database names, immutable manifest names, and SHA-256 digests. This respects B2’s 50-byte metadata-key limit while preserving the full 64-byte database-name contract. One dedicated bucket holds one cluster prefix. Unrelated metadata is preserved; lifecycle, public access, and retention fields are never changed by the adapter.

A writer reads the bucket revision, uploads a fresh manifest, then replaces bucket info with `ifRevisionIs`. A revision collision during publication returns a conflict. Before uploading the manifest, the adapter compares the database pointer identity; unrelated earlier metadata changes need not conflict. A failed response may have committed; the engine's transaction receipt recovers it. The adapter never republishes the same uploaded manifest against a later bucket revision.

Reads fetch bucket metadata, conditionally validate it with a fresh read fence, then fetch the referenced manifest, verify its hash, and load immutable pages as needed. The successful conditional update is the read linearization point. If collection removes an old manifest in between, the whole manifest fetch restarts. Atomic revision checking is the safety assumption. Bucket listings may be stale: the read barrier retries a definite revision conflict and fails closed if it cannot validate within its bounded retry budget. It does not infer metadata freshness from file-visibility documentation. `spec/ReadBarrier.tla` models stale observations and conditional validation; its negative control returns stale data when validation is omitted.

## Two collection layers

The engine's original fence protects data pages. A second collector protects the immutable manifests: list candidates first, read the complete current pointer set, conditionally update bucket metadata with a fresh fence, then delete only listed manifests outside the protected set. A paused publisher loses its revision comparison. The collector can die at any step without making its deletion authority transferable to a new attempt.

B2 always keeps file versions. Collection uses native `b2_list_file_versions` and `b2_delete_file_version`; S3 delete markers would leave the billed bytes behind. Duplicate versions caused by upload retries are deleted in bounded batches. No external retention/lifecycle policy may delete live database objects.

The same `publication::Published` code runs on S3; only wire operations differ. `spec/Bucket.tla` models two database slots, two pods, two attempts, and three bucket revision advances. It checks manifest reachability through crashes, partitions, stale writers, and concurrent collection. Its intentionally broken variant omits the fence and produces a missing-manifest counterexample. This complements the engine model; composition/refinement into Rust is not a completed proof.

## Initial limits and performance

The flat metadata directory admits at most 32 databases and 9,000 serialized metadata bytes per bucket. An oversized update fails before uploading its manifest. This leaves room below B2's metadata ceiling but unrelated metadata can reduce capacity. Database data limits remain separate.

All metadata writes in a bucket serialize. Scaling pods adds request concurrency, not unlimited write throughput for that bucket. Reads currently perform a bucket listing, a conditional metadata update, and an immutable manifest fetch; there is no stale manifest cache. Group commit and a partitioned multilevel directory are future format work, not current performance claims. Measure metadata throttling and latency before sizing a deployment. Provider upload/download rate limits are not a guarantee of metadata-update throughput.

## Configuration

```sh
export B2_APPLICATION_KEY_ID=...   # service-side credential, never a tenant token
export B2_APPLICATION_KEY=...
durable-db serve --listen 0.0.0.0:7654 --b2-bucket dedicated-private-bucket \
  --admin-key-file /run/secrets/admin.key
```

The key needs `listBuckets`, `writeBuckets`, `readFiles`, `writeFiles`, `listFiles`, and `deleteFiles` for this bucket. Native authorization refreshes after token expiration. HTTP timeouts and upstream failure messages do not expose credentials to tenants. Startup checks that a stale revision is rejected.

A seven-day key restricted to the disposable test bucket successfully performed native revision publication and version deletion using B2 API v4. The account-wide operator key was used only to provision that bucket and workload key; it was not mounted into the database. Follow that separation in deployments. Check capabilities against the actual key type/API version rather than assuming every scoped key behaves identically.

## Qualification evidence

The real-B2 test created a database, committed five revisions, recovered identical receipts, reclaimed old pages and manifests by file version, and reopened with a new client and empty cache. It passed in about ten seconds. It uses `DURABLE_DB_TEST_B2_BUCKET` with `cargo test --test b2_cloud -- --ignored --nocapture`. Only use a dedicated test bucket; the test retains the final database for inspection.

Live API probes confirmed that a genuinely different stale bucket update returns `409 conflict`, while an identical-metadata no-op may return success without advancing revision. The shared startup probe accounts for this behavior. The directory encoding also exercises database names longer than B2's metadata-key ceiling.

Long-running cloud contention, provider throttling, network fault injection, and Kubernetes HPA scenarios remain qualification work. The conditional read barrier is enabled unconditionally and must not be removed based only on optimistic benchmark results.
